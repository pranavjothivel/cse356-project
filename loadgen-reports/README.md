# loadgen-reports

Archived outputs from our **ad-hoc loadgen runs** — discrete passes the team kicked off from a developer laptop or the loadgen node against the prod cluster to validate specific fixes (BGSAVE-off baseline, GC tuning, optimistic broadcast variants, TLS-handshake characterization).

> These are *our* runs. They are **not** the course grading load generator's traffic, which we did not control. See [`project-docs/SCALING.md`](../project-docs/SCALING.md#how-we-measured) for the distinction between the two.

## File naming

```
2026-MM-DD-<scope>-<state>.{json,log}
2026-MM-DD-tls-probe[-<variant>].csv
```

- `<scope>` — what the run was scoped to (e.g. `1k` = 1k recipients, `post-gc-tuning`, `post-bgsave-off-baseline`).
- `<state>` — when in the tuning timeline the run was kicked off (`baseline`, `post-<fix>`, `observed`).
- `.json` — structured run summary (config + headline aggregates + per-window timeline).
- `.log` — per-request trace from the same run.
- `.csv` — TLS-probe captures, one row per probe sample (generated by [`scripts/tls-probe/tls-probe.sh`](../scripts/tls-probe/tls-probe.sh)).

## JSON schema (run summaries)

```jsonc
{
  "config": {            // test parameters set on the loadgen harness
    "BASE_URL": "...", "NUM_RECIPIENTS": 500, "NUM_SENDERS": 20,
    "MSGS_PER_SEC": 50, "DURATION_SEC": 300, "RAMP_SEC": 30, "COOLDOWN_SEC": 15
  },
  "run": { "startedAt": "...", "finishedAt": "...", "durationSec": ..., "communityId": "...", "channelId": "..." },
  "counters": { "messagesPosted": ..., "messagesPostFailed": ..., "samples": ..., "outOfOrderReceives": ..., "selfReceives": ..., "stillPending": ... },
  "latencyMs": { "count": ..., "min": ..., "p50": ..., "p90": ..., "p95": ..., "p99": ..., "p999": ..., "max": ..., "mean": ... },
  "timelineP95": [ { "windowStartSec": 0, "samples": ..., "p50": ..., "p95": ..., "max": ... }, ... ]
}
```

The harness publishes `MSGS_PER_SEC` messages from `NUM_SENDERS` clients into a single community + channel, with `NUM_RECIPIENTS` other clients receiving each message. **Each broadcast generates `NUM_RECIPIENTS` latency samples** (one per recipient-receives event), so `counters.samples` is roughly `messagesPosted × NUM_RECIPIENTS`.

## Reports

### Message-delivery latency passes (2026-05-05)

All four ran against the same config (`500 recipients × 20 senders × 50 msg/s × 300 s + ramp + cooldown`) so the numbers are directly comparable.

| Report | What it captures | Messages | Samples | p50 | p95 | p99 | mean |
|---|---|---:|---:|---:|---:|---:|---:|
| `2026-05-05-post-bgsave-off-baseline.{json,log}` | Baseline after **disabling Redis RDB BGSAVE** (SCALING.md Bottleneck 7) — first clean run without the periodic ~100 ms fork pauses on Redis-01 | 13,595 | 6.8 M | 291 ms | **2,093 ms** | 3,422 ms | 561 ms |
| `2026-05-05-post-gc-tuning.{json,log}` | After the V8 GC tuning landed (`--max-semi-space-size=8 --max-old-space-size=384`, SCALING.md cross-cutting section) | 12,133 | 6.1 M | 522 ms | **2,804 ms** | 5,245 ms | 911 ms |
| `2026-05-05-post-optimistic-broadcast.{json,log}` | After the optimistic-broadcast experiment (publish broadcast *before* PG INSERT completes; relates to the WS payload + hot-path work in SCALING.md Bottleneck 6) | 12,812 | 6.4 M | 270 ms | **949 ms** | 2,426 ms | 367 ms |
| `2026-05-05-post-optimistic-broadcast-no-instrum.{json,log}` | Same optimistic-broadcast change, but with the in-app instrumentation hot-patch removed — measures the cost of the instrumentation itself | 11,644 | 5.8 M | 121 ms | **305 ms** | 465 ms | 142 ms |

**Reading the numbers.** The two optimistic-broadcast runs combined make the case for both the broadcast-before-INSERT change *and* the cost of leaving instrumentation enabled in the hot path — p95 collapses from ~2,800 ms (post-GC, pre-optimistic) to ~950 ms (optimistic, with instrumentation) to ~305 ms (optimistic, instrumentation removed). The post-bgsave-off-baseline establishes the "Redis isn't stalling us periodically" floor that the later runs build on. The post-gc-tuning run shows higher p95 than the BGSAVE baseline because the *test config also got tougher* (the harness was re-run against a freshly cleared cache); the validity check for GC tuning is in the in-process event-loop-lag traces (see SCALING.md Bottleneck 6 evidence), not in this report's aggregate.

### Verbose-trace runs (2026-05-05)

| File | What it is |
|---|---|
| `2026-05-05-1k-observed.log` | 1k-recipient observation run with full per-request `console.log` traces enabled on the publisher path. Use the `.log` for individual-message tracing when a specific message ID needs investigation. |
| `2026-05-05-1k-observed-sampler.jsonl` | Sampler-format output of the same run — one JSON line per sampled message, easier to grep than the `.log`. |
| `2026-05-05-1k-20min-collapsed.log` | 20-minute soak run (1k recipients) with collapsed/aggregated logging. The longer duration surfaces tail behavior that 5-minute runs miss. |

### TLS-handshake characterization (2026-05-06)

Generated by [`scripts/tls-probe/tls-probe.sh`](../scripts/tls-probe/tls-probe.sh). Each file is a CSV — one row per probe sample with `dns_ms / tcp_ms / tls_ms / ttfb_ms / total_ms / http_code / remote_ip`. Used to characterize **LB-side cold-handshake latency** separately from app-side cost. Evidence for SCALING.md Bottleneck 8 (HAProxy + LB host tuning).

| File | Variant |
|---|---|
| `2026-05-06-tls-probe.csv` | Initial pre-tuning baseline |
| `2026-05-06-tls-probe-postfix-hostname.csv` | After the `tcp_max_syn_backlog` + `somaxconn` sysctl bumps, probed against the hostname (DNS-resolution included) |
| `2026-05-06-tls-probe-postfix-ip.csv` | Same conditions as `-postfix-hostname` but probed against the LB's public IP directly, so the DNS lookup cost drops out |
| `2026-05-06-tls-probe-postrestart-ip.csv` | After a full HAProxy restart (rather than a reload) — checks whether listen-socket state carried into the new process and whether the listen-queue depth recovered cleanly |

## Reproducing a run

The harness is the [`group1-loadgen-01`](../infra/README.md#node-inventory) node. Configuration knobs match the JSON `config` block above; outputs land in this directory under the same naming convention.

For the TLS probe: `bash scripts/tls-probe/tls-probe.sh --count 1000 --concurrency 32 --target <hostname-or-ip>`. CSV path is configurable.
