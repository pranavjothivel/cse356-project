## Root Cause: PostgreSQL Connection Pool Exhaustion

### Mechanism

Sequelize uses its default pool: **max 5 connections per worker**. With 2 workers per node, each node has 10 total DB connections. The autograder floods the system with hundreds of concurrent requests. The busiest endpoint — `POST /api/conversations/:id/read` — makes **7–8 sequential DB queries per request**:

1. `Conversation.findByPk(id)` — always runs first, even for channel IDs (wasted query)
2. `Channel.findByPk(id)` — fallback when #1 finds nothing
3. `ChannelMember.findOne` — membership check
4. `Message.findOne` — verify message belongs to this channel/conversation
5. `Message.findByPk(currentId)` — inside `isForwardRead()`, fetches old message to compare timestamps
6. `member.save()` — UPDATE last_read_message_id
7. *(conversations only)* `listParticipants(conv.id)` — fetches all participants for broadcast

When all 10 connections are busy, new requests queue. Sequelize's default `pool.acquire` timeout is **60 seconds** — longer than HAProxy's `timeout server 50s`. HAProxy fires first → 504.

## Secondary Issues

### 1. MinIO auth broken on node-01

Every upload request on node-01 fails with:
```
S3Error: The Access Key Id you provided does not exist in our records.
  code: 'InvalidAccessKeyId'
```
`MINIO_ACCESS_KEY` in `/srv/app/.env` on node-01 is wrong or has been rotated.

### 2. MinIO ECONNREFUSED on node-02

node-02 was logging `ECONNREFUSED 10.0.1.28:9000` — MinIO was unreachable. Resolved itself (MinIO is reachable now), but no connection timeout is configured on the MinIO client, so if it goes down again requests will hang until the OS-level TCP timeout fires.

### 3. CPU saturation on node-02

Both node-02 workers have been pegged at ~65% CPU each (130% on a 2-vCPU machine), with a sustained load average of 1.47–1.48 for 8+ hours. Likely driven by bcrypt on concurrent logins + the heavy DB-query handlers all queuing simultaneously.

### 4. Broken SQL in unread channels query (now fixed after redeploy)

A prior version of the code running on node-01 until ~16:20 UTC was generating invalid PostgreSQL:
```sql
WHERE cm.channel_id = ANY('uuid1', 'uuid2', 'uuid3')
```
PostgreSQL's `ANY()` requires an array, not a parenthesized list. Should be:
```sql
WHERE cm.channel_id = ANY(ARRAY['uuid1', 'uuid2', 'uuid3'])
-- or use IN:
WHERE cm.channel_id IN ('uuid1', 'uuid2', 'uuid3')
```
This caused every call to the affected endpoint to return a 500. Fixed after the 16:20/16:28/16:45 redeploys.

## Fixes Required

### Fix 1 — Increase Sequelize connection pool (critical)

**File:** `server/src/db.js`

```js
const sequelize = new Sequelize(process.env.DATABASE_URL, {
  dialect: 'postgres',
  logging: false,
  pool: { max: 20, min: 2, acquire: 30000, idle: 10000 },
  dialectOptions: process.env.NODE_ENV === 'production'
    ? { ssl: { require: true, rejectUnauthorized: false } }
    : {},
});
```

`max: 20` gives 40 total connections per node (2 workers). Keep `acquire` below HAProxy's 50s timeout so callers get a real error instead of a silent 504.

### Fix 2 — Eliminate the double-lookup in `/read` (high)

`POST /api/conversations/:id/read` always tries `Conversation.findByPk` first, then `Channel.findByPk`. Since the autograder routes channel read receipts through this endpoint using channel IDs, the first query is always wasted. Fix: run both lookups in parallel, or check the ID format/prefix to decide which table to query first.

```js
// Run in parallel instead of sequentially
const [conv, channel] = await Promise.all([
  Conversation.findByPk(req.params.id),
  Channel.findByPk(req.params.id),
]);
```

### Fix 3 — Eliminate `isForwardRead`'s extra DB query (medium)

`isForwardRead(currentId, newMsg)` fetches the old message by PK to compare `createdAt`. This is an extra round-trip on every read receipt that has a previous pointer. Options:
- Store `last_read_message_created_at` alongside `last_read_message_id` on the participant/member row so the comparison is in-memory.
- Pass the already-fetched old message object if it's available in the call site (it isn't today, but restructuring is possible).

### Fix 4 — Fix MinIO credentials on node-01 (high)

```bash
# On node-01 (130.245.136.217):
ssh deploy@130.245.136.217
nano /srv/app/.env  # update MINIO_ACCESS_KEY and MINIO_SECRET_KEY
pm2 reload ecosystem.config.js --update-env
```

Or update `ENV_FILE` in GitHub Secrets and push to trigger a deploy.

### Fix 5 — Add MinIO connection timeout (medium)

The MinIO client has no explicit connection timeout. If the MinIO host goes down, upload requests will hang until the OS TCP timeout (~2 min), holding a Node.js worker thread. Add a timeout in the Minio client config or wrap calls with a `Promise.race` timeout.

### Fix 6 — Move sessions to Redis (medium, already planned)

`connect-pg-simple` adds a DB query for every session lookup — that's +1 DB query on every authenticated request. Moving to `connect-redis` (already in the architecture plan) removes this entirely and reduces pool pressure.
